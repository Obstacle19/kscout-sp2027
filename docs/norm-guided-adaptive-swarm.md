# Norm-Guided Adaptive Swarm：当前工作机制

本文记录 KScout 当前实现的协作机制，并区分工程能力与尚待实验验证的研究目标。

## 设计定位

KScout 使用**无固定角色、由协调器调度、按轮次共享证据**的 peer swarm。Agent 可以提出、质疑、复现或扩展任意线索；协调器负责分配下一轮任务和控制总预算。当前轮次之间共享信息，不提供实时 Agent-to-Agent 群聊。

## 当前流程

1. **独立探索。** 首轮 peer 在独立工作区审查源码并提交线索；它们不会看到同一轮其他 peer 的结论。
2. **记录证据与交互。** 协调器汇总论证板、结构化事件日志和 Lead 索引。事件可记录参与者、动作、线索、证据引用、探索区域、信息增益和资源使用；有效证据引用必须指向 peer 工作区中的文件。负面、拒绝和暂停状态会保留，历史 finding 索引可用于跨运行排重。
3. **按信息缺口调度。** 后续任务优先处理复现缺口、安全影响和未解决争议，并考虑新证据及历史 Token/时长成本。默认将约 25%–40% 的后续 session 留给新方向探索；反复无进展的 Lead 可暂停并保留证据，出现同根因新证据时可重新激活。首次跟进采用上下文级盲挑战。
4. **分开记录复现与结论。** `CANDIDATE`、`AGENT_REPRODUCED` 和 `CROSS_REPRODUCED` 描述 Agent 报告的状态；两个 peer 报告本地执行不等于独立根因分析或外部验证。可选外部 verifier 检查运行结果、源码版本、配置摘要、正例、负对照和证据文件。`REPORTABLE` 与 `SECURITY_CONFIRMED` 需要单独的独立评审记录。
5. **冻结规范并按评估更新。** 每次运行使用一个版本化规范集。运行轨迹和评估反馈可用于生成下一版本的资源参数与交互指导。更新器要求 baseline 与 norm-guided 条件匹配、固定总预算、独立架构盲审、至少 3 个任务和 3 次重复，并且只接受 train 或 validation 数据；轨迹归纳是启发式更新，不证明规范带来因果改善。

## 目前能做什么、还不能证明什么

- 每轮可配置 2–16 个 Agent、最多 4 轮；单次运行最多 64 个 child session。支持 10+ Agent 的配置不等于已经证明该规模更有效。
- 首次 Lead 挑战只做提示与上下文级盲化。当前工作区配置没有阻止 Agent 自行读取上级目录，因此不构成严格的信息隔离。
- 外部 verifier 由使用者提供。协调器检查结构化结果与证据路径，但不能仅凭 verifier 输出证明 VM 的隔离实现；同样，评估输入中的盲审声明也由评估者提供。
- 代码提供事件记录、策略更新和结果状态，不代表已完成 10、12 或 16 Agent 的对照实验，也不保证发现率、精确率或 Token 效率提升。
